# SolarPower AI: Project Report

**Weather-Aware Solar Panel Power Output Prediction Using Supervised Machine Learning**
Category: Supervised Learning (Regression)

> **Data honesty note.** All results in this report come from a **synthetic** dataset generated by
> `backend/app/data_gen.py`. It is not measured data. Because the target is produced by a formula, the models
> score very high; these scores show that the pipeline is correct, not how accurate it would be on a real plant.

## 1. Abstract

Solar power output varies with sunlight, cloud cover, temperature, humidity and wind, which makes it hard to schedule
and integrate into the grid. This project presents SolarPower AI, a supervised-regression application that predicts
solar panel output in kilowatts (kW) from six environmental inputs: solar irradiance, temperature, humidity, wind speed,
cloud cover and hour of the day. Five algorithms (Linear Regression, Decision Tree, Random Forest, Extra Trees and
Gradient Boosting) are trained with a chronological train/test split, tuned with time-series cross-validation and
compared using MAE, MSE, RMSE and R², against a mean-prediction baseline. On the bundled synthetic dataset the best
model, Random Forest, reached R² = 0.9977 and RMSE = 0.048 kW on unseen later data. The system
is delivered as a FastAPI backend and a React dashboard with prediction, model comparison, data visualisation, what-if
analysis and feature-importance pages. The pipeline accepts real datasets without code changes.

## 2. Problem statement

Given weather conditions at a given hour, predict how much electricity (kW) a solar panel system will generate.
Accurate forecasts help house owners plan consumption, and help grid operators balance supply and demand.
Physical formulas need many panel-specific parameters, so a data-driven model that learns directly from weather
and output records is a practical alternative.

## 3. Objectives

1. Build a regression model that predicts solar output (kW) from six weather features.
2. Train and compare five regression algorithms using MAE, MSE, RMSE and R².
3. Use a chronological split and time-aware cross-validation to avoid data leakage.
4. Identify which environmental factors influence the predictions.
5. Provide an interactive dashboard for prediction, comparison, exploration and what-if analysis.

## 4. Dataset

| Item | Value |
|---|---|
| Type | **Synthetic** (generated, not measured) |
| Generator | `backend/app/data_gen.py`, fixed random seed 42 |
| Size | 17520 hourly rows, 2023-01-01 00:00:00 to 2024-12-30 23:00:00 (2 years) |
| System | assumed 5 kW rooftop installation at about 26°N |

**How it is generated.** Solar position (declination and hour angle) gives clear-sky irradiance. A persistent random
process with a monsoon-like season gives cloud cover, which reduces irradiance. Temperature, humidity and wind are
generated with daily and seasonal cycles and noise. Power = capacity × irradiance/1000 × temperature efficiency
(about −0.4 % per °C of cell temperature, where wind cools the cell) × system losses × a small humidity factor × 3 % noise.
Missing values (about 1 % per feature) are injected on purpose so the cleaning step has real work to do.

### Features and target

| Column | Unit | Role | Explanation |
|---|---|---|---|
| timestamp | date-time | index | Used only for sorting and splitting; not a model input |
| irradiance | W/m² | feature | Solar power per square metre reaching the panel; main driver of output |
| temperature | °C | feature | Ambient air temperature; hotter panels convert less efficiently |
| humidity | % | feature | Relative humidity; small negative effect |
| wind_speed | m/s | feature | Cools the panel, improving efficiency |
| cloud_cover | % | feature | Share of sky covered by cloud; reduces irradiance |
| hour | 0-23 | feature | Time of day; encoded as sine and cosine |
| **power_kw** | kW | **target** | Electricity generated by the panel system |

## 5. Methodology (ML workflow)

1. **Load and validate**: check that all required columns exist.
2. **Clean** (`app/data.py`): sort by time; drop duplicate timestamps; convert to numbers; mark physically impossible values
   (outside the ranges in `config.py`) as missing; drop rows whose target is missing; clip negative power to 0.
   In this run 41 rows had no target and were dropped (17520 -> 17479 rows).
   Missing feature values before imputation: irradiance: 207, temperature: 167, humidity: 178, wind_speed: 150, cloud_cover: 164.
3. **Feature engineering** (`app/features.py`): `hour` becomes `hour_sin` and `hour_cos`, so hour 23 is next to hour 0.
4. **Imputation**: median of each feature, **fitted only on the training data** inside the scikit-learn `Pipeline`.
   Linear Regression additionally uses `StandardScaler`.
5. **Chronological split**: the oldest 80 % (13984 rows, up to 2024-08-06 21:00:00) train the model; the newest
   20 % (3495 rows, from 2024-08-06 22:00:00) are used only for the final test. Random shuffling is avoided because
   neighbouring hours are similar, and shuffling would let the model "see the future".
6. **Baseline**: a model that always predicts the training mean. Any useful model must beat it.
7. **Hyper-parameter tuning**: `GridSearchCV` with `TimeSeriesSplit(3)` on the training set (scoring: RMSE).
8. **Evaluation** on the test set with MAE, MSE, RMSE and R². Predictions are clipped at 0 because power cannot be negative.
9. **Explanation**: built-in importance for tree models and permutation importance for all models.
10. **Persistence**: the whole pipeline (preprocessing + model) per algorithm is saved with Joblib; metrics are saved as JSON.

### Algorithms

| Algorithm | Idea | Note |
|---|---|---|
| Linear Regression | Fits a straight-line relationship | Simple, fast, cannot capture curves such as the day/night switch |
| Decision Tree | Splits data with yes/no questions | Captures non-linearity; a single deep tree can overfit |
| Random Forest | Averages many trees trained on random samples | More stable than one tree |
| Extra Trees | Like Random Forest with random split points | Faster, often similar accuracy |
| Gradient Boosting | Builds trees one after another, each fixing the previous errors | Often the most accurate, slower to tune |

### Metrics

- **MAE**: average absolute error in kW (easy to interpret).
- **MSE**: average squared error (penalises large mistakes).
- **RMSE**: square root of MSE, in kW.
- **R²**: share of the variance explained (1 = perfect, 0 = no better than the mean).

### Selected hyper-parameters

| Model | Best parameters found |
|---|---|
| Linear Regression | `none (no tuning)` |
| Decision Tree | `{'max_depth': 10, 'min_samples_leaf': 5}` |
| Random Forest | `{'max_depth': 10, 'min_samples_leaf': 3, 'n_estimators': 100}` |
| Extra Trees | `{'max_depth': 14, 'min_samples_leaf': 3, 'n_estimators': 150}` |
| Gradient Boosting | `{'learning_rate': 0.05, 'max_depth': 4, 'n_estimators': 200}` |

## 6. Results

Test set = newest 3495 hours. Lower is better for MAE, MSE, RMSE; higher is better for R². "CV RMSE" is the
cross-validated error inside the training data.

| Model | MAE | MSE | RMSE | R² | CV RMSE |
|---|---|---|---|---|---|
| Baseline (mean) | 0.9078 | 1.0148 | 1.0074 | -0.0207 | - |
| Linear Regression | 0.0517 | 0.0175 | 0.1321 | 0.9824 | 0.1504 |
| Decision Tree | 0.0231 | 0.0030 | 0.0545 | 0.9970 | 0.0747 |
| Random Forest ★ | 0.0205 | 0.0023 | 0.0478 | 0.9977 | 0.0662 |
| Extra Trees | 0.0204 | 0.0023 | 0.0480 | 0.9977 | 0.0717 |
| Gradient Boosting | 0.0218 | 0.0025 | 0.0501 | 0.9975 | 0.0624 |

**Observations**

- The baseline R² is about zero, so the real models are learning genuine structure.
- Linear Regression is clearly the weakest because the day/night behaviour and the efficiency effects are not linear.
- The four non-linear models are close to each other. Differences in the third decimal place are small and could change with another random seed or data sample, so the "best" model should not be over-interpreted.
- Test RMSE is lower than CV RMSE. A likely reason is that the early cross-validation folds train on much less data (the first fold uses only a quarter of the training period), but this was not investigated further.

### Feature importance (Random Forest)

- Built-in (tree) importance: irradiance 0.983, hour 0.014, temperature 0.001, cloud_cover 0.001, wind_speed 0.000, humidity 0.000
- Permutation importance (drop in R² when shuffled): irradiance 1.214, hour 0.936, cloud_cover 0.003, temperature 0.001, wind_speed 0.000, humidity 0.000

Irradiance dominates, as expected from the physics. Hour also matters because it tells the model whether the sun is up.
Cloud cover shows a small score because its effect already passes through irradiance (the two features are correlated);
importance scores of correlated features can hide each other. Temperature, humidity and wind change efficiency by only a few
percent, so their scores are small even though they are physically real. A permutation value above 1 means that shuffling
the feature made the model worse than predicting the mean.

## 7. System design

- **Backend (FastAPI)** exposes `/api/predict`, `/api/whatif`, `/api/scenarios`, `/api/predict-batch`, `/api/metrics`,
  `/api/importance`, `/api/viz/*` and others. Inputs are validated (ranges and types); errors return clear messages.
  `app/service.py` contains the logic and has no web code, so it is unit tested directly.
- **Frontend (React + Recharts)** has pages for Home, Prediction, Model comparison, Data visualisation, What-if analysis,
  Model explanation and Batch prediction. It reads everything from the API, so metrics shown are always the real ones.
- **Tests** (`backend/tests/test_core.py`) check the data columns, cleaning, the chronological split, that every model beats
  the baseline, non-negative predictions, the what-if direction, input validation, chart data and missing-model errors.

## 8. Limitations

- The data is synthetic; real plants have shading, dust, inverter limits, panel ageing and sensor errors that are not modelled.
- The models are trained for one assumed plant (5 kW, one location). They do not transfer to other plants.
- Hourly data only; no forecasting of future weather (the user supplies the weather).
- Hyper-parameter grids are deliberately small to keep the project simple.
- Observed R² near 1 is expected on formula-generated data and must not be quoted as real-world accuracy.

## 9. Future work

Train on measured plant data; add weather-forecast inputs and lag features; try quantile/probabilistic forecasts;
add panel tilt and plant capacity as features; deploy the API and frontend online.

## 10. Conclusion

SolarPower AI shows a complete supervised-regression workflow: data cleaning, feature engineering, leakage-free
chronological evaluation, model comparison with four metrics, explanation and an interactive dashboard. On the synthetic
dataset the non-linear ensemble models and the single tree predict output far better than Linear Regression and the baseline,
and irradiance and time of day are the most influential inputs. The same code can be retrained on real measured data
with one command to obtain meaningful real-world accuracy.
